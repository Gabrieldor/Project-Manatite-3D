## Player ship
- Movement model: **6DoF free-flight, Newtonian** (thrust-based; no auto-stop). Gamepad:
  left stick = translate (forward/back + strafe), right stick = pitch/yaw (non-inverted, up=nose up),
  LT/RT = descend/ascend, LB/RB = roll, R3 = target lock. First-person **cockpit camera** rigidly mounted. Tunables in `ShipMovement_Default.asset`.
- Target lock: R3 acquires the `Lockable` object nearest screen center (within a viewport radius); while locked, the ship auto-turns its nose onto the target (camera stays rigidly mounted — no independent camera movement). While locked, flicking the right stick switches the lock to the nearest other `Lockable` in that screen-space direction relative to the current target (within a search radius/cone; no qualifier = no-op). R3 again releases. Tunables in `TargetLock_Default.asset`.
- Weapons: **Primary fire** — RB spawns pooled forward-traveling projectiles (placeholder cube), despawn on hit or after a lifetime timeout. Fire mode (Auto/Single) and all tunables live in `WeaponData` assets (default: `Weapon_Default.asset`). Modifier system planned but not built: `Projectile` exposes an `OnHit` C# event as the future attachment point instead of injecting code into the bullet directly. Secondary weapon/pickups/heat/ammo: *TBD*.
- Health/shield: **10 HP**, no shield layer yet. `Health` component (generic, shared with enemies) + `Health_Player.asset` (`HealthData`, `maxHealth: 10`). No HUD or death/respawn handling yet — *TBD*.

## Enemies
- **Basic Enemy**: capsule placeholder model, straight-line pursuit of the player, no attack yet. Tunables in `EnemyMovement_Basic.asset`.
- **Spawn rule**: proximity-triggered. Each planet carries its own trigger zone (radius = its scale × a per-type multiplier range); entering it spawns a configurable roster (which enemies, how many, all-at-once or timed waves) around the ship's current position. Config lives in `EnemySpawnData` assets, one per planet type (`EnemySpawn_Lava/Ice/Acid.asset`). Zones re-arm 30s after their encounter finishes spawning.
- *TBD: other archetypes (shooter, tank, boss); enemy attacks/health/death.*

## Planets
- **Procedural placement**: 3 planets spawn once at scene start via `PlanetSpawner`, each independently and randomly typed (lava/ice/acid — duplicates allowed), scattered at random non-overlapping positions across the playable field. Config lives in `PlanetSpawnData` (default: `PlanetSpawn_Default.asset`). Each type's visuals, size range, and encounter-trigger radius range live in its `PlanetData` asset (`PlanetData_Lava/Ice/Acid.asset`), which also points at that type's `EnemySpawnData` roster. `Planet.prefab` = visual sphere + encounter-trigger child.

| 2026-07-21 | Crosshair reacts to lock via a center-reticle color swap plus a marker that tracks the locked target's screen position, not new shape/art | Built-in UI Image only, no new texture/art pipeline (see `specs/crosshair.md`) |
| 2026-07-29 | Damage and health are always `int`, never `float`; all projectiles deal 1 damage by default (player and enemy weapon data) | User directive — whole-number combat values only, no fractional damage/health |
| 2026-07-29 | Player has 10 HP via the existing `Health` component + new `Health_Player.asset` (`HealthData`) | Reuses the enemy combat `Health` class as-is per BACKLOG item 1; HUD/death handling still TBD |
| 2026-07-29 | Player death (`Health.OnDied`) quits the app (or stops Play Mode in-editor) via a new `PlayerDeath` component | User directive — placeholder game-over until a real death/respawn flow exists |
| 2026-07-29 | Raised `EnemyData` `stopDistance` per enemy size (Basic 15→28, Medium 15→45, Large 15→95) | User-reported enemies missing most shots at point-blank range even vs. a stationary player; root cause was the old shared `stopDistance: 15` sitting well inside each enemy's own (scaled) hull — Medium/Large hulls reach 33/83 units from their pivot, so they were holding position while overlapping the player, and the resulting collision jitter kept corrupting their aim before it could settle |
| 2026-07-29 | Scaled `NavePrincipal` root 1x→6x (ship now ~20×23×30 units, comparable to the Basic enemy's ~20-unit collider) | Root cause of the miss rate was mostly this: the player ship's hand-built cube hull was internally consistent but ~4-8x smaller than even the Basic enemy, an easy target to overshoot at the enemy's aim precision. User initially asked to copy the enemy's `Model`-child `1000` scale, but that factor only corrects *that* enemy's raw imported mesh's tiny native units — applying it to the ship literally would've made it ~3.4km long and (since `CameraMount`/`FirePoint` are siblings of `Model`, not scaled with it) buried the cockpit camera inside the hull. Scaled the root instead so mesh/collider/camera/fire point all move together proportionally. `stopDistance` values above were re-tuned after this to account for the player's now-larger collider |
| 2026-07-29 | `EnemyController`'s aim `Quaternion.LookRotation(dir, up)` falls back to `Vector3.forward` as the up-reference when `dir` is nearly parallel to world up | User reported settled, non-turning enemies still firing off-target intermittently. Root cause: full 6DoF free-flight means enemies (spawned at random points on a sphere around the player) regularly end up nearly directly above/below the player, where `LookRotation` with a fixed world-up reference is numerically unstable and can snap to a wrong heading for a frame even though the enemy looks locked on |
| 2026-07-29 | ~~Raised `EnemyData.moveSpeed`~~ — reverted, wrong diagnosis, `moveSpeed` stayed at `12` for all types | User corrected this: enemies going quiet while the player moved wasn't a speed/leash issue, it was the same vertical-miss bug below (see next entry) — the "not shooting" was actually "shooting but always missing," misread as enemies falling out of range |
| 2026-07-29 | Enemies aim at a new `AimPoint` child on the player ship (world `(0, 15.75, 0.22)`) instead of the ship's raw transform pivot; `EnemySpawnZone` resolves `rb.transform.Find("AimPoint")` once per encounter trigger and passes that to `EnemyController.Initialize` | **This was the actual root cause of "enemies shooting toward another direction."** Live-captured a real shot: the enemy's yaw was dead-on (`velDir` exactly matched the direction to the player's pivot), but the ship's hand-built cube hull was never centered on its own transform origin — after the 6x scale fix, the hull's real geometric/collider center sits at world `Y≈9-19` while the pivot (what enemies were aiming at) is `Y=0`. Every shot flew level under the entire hull, a total whiff at typical engagement ranges (28-95 units), not a rounding-error miss. Confirmed fixed live: an enemy that previously did 0 damage over a full engagement dealt 8 damage (10→2 HP) once retargeted at `AimPoint` |
| 2026-08-04 | Pause menu's Quit returns to the Main Menu scene, not `Application.Quit()`; pausing freezes the whole game via `Time.timeScale = 0` rather than disabling individual gameplay scripts | Since all ship/enemy/projectile motion already lives in `FixedUpdate`, zeroing `Time.timeScale` freezes it for free with no per-script pause flags; "Quit" meaning "leave this run" (vs. the Main Menu's own Quit, which already covers exiting the app) matches standard genre convention (see `specs/pause-menu.md`) |
| 2026-08-04 | Save/load persists a single run (health + the exact procedural planet layout, keyed by a stable per-run `planetId`, not RNG-seed replay) via one JSON save slot; a planet's `beaten` flag is now real, set true only when every enemy from its encounter is killed (fleeing/leashing them away doesn't count), which also autosaves | Only state that exists today is saved — no money/economy, chip inventory, or NPC-purchase systems yet, so nothing was added for those (schema is additive-safe for later); "clearing the wave" as the autosave trigger needed real kill-tracking on `EnemySpawnZone`, not just its existing spawn-finished cooldown (see `specs/save-load-system.md`) |
| 2026-07-31 | Replaced the 3 hand-placed lava/ice/acid planets (plus 7 orphaned, ad hoc `Planet_XX_SpawnZone` encounter triggers not physically tied to any of them) with `PlanetSpawner`: 3 planets spawn once at scene load, each independently random-typed, positioned, sized, and given its own randomized encounter-trigger radius within data-driven min/max ranges, each wired to a per-type `EnemySpawnData` roster | User directive to make planet placement procedural. Field volume for placement is the GDD-documented playfield box (what `farClipPlane` was tuned to cover), not a raw sphere from the origin — spawning outside the documented play volume made no sense. One-time spawn at scene start, not continuous, since the playable field is a fixed bounded box, not infinite (see `specs/procedural-planets.md`) |
